# Field notes

Lessons from bringing this layer up against a live residential deployment.
Written for whoever configures it against a different site. No measurements,
addresses, or building details from the original deployment appear here.

## Verify the feature contract from the artifact, never from documentation

The served models took a different feature count from what the project's own
written record claimed. Several sets of exported artifacts sat side by side in
the models directory, differing in feature count and in their head lists, and
only one set was actually loaded by the inference loop.

The check that settled it took two steps. Read the module that names the model
paths, then read the normalization JSON at those exact paths. Confirm the
answer against reality by comparing the head list in the artifact to the
distinct appliance values present in the live inference output table. The set
that matches is the one being served.

`scripts/verify_site.py` automates the second half of this. Run it before
trusting `config/site.yaml`, and again before any demo.

## Check the sign convention before deriving anything from it

On the deployment this was built against, subpanel power channels read
negative, while the normalization means stored in the model artifacts were
positive. A subpanel does not generate, so one of three things was true: the
meter registers were configured with reversed polarity, the ingestion producer
negated, or the model was trained on one sign and served the other.

The third possibility is the dangerous one. If training saw positive watts and
inference sees negative, every appliance estimate is produced from inputs the
model never encountered, and the estimates are not wrong so much as
meaningless.

The corroborating symptom was implausible inference output. Several
intermittent appliances were reported continuously on for an entire window,
duty cycle 1.00, zero switches. A microwave does not run for thirty minutes.

Settle the sign convention before evaluating any category whose definition
rests on the magnitude or direction of power, and before promoting any window
to a training example.

## Expect no anomaly history

The deployment had an anomalies table with two rows, both from a pipeline
verification run. This is normal. Detection systems get built before anyone has
labeled anything, so the honest starting point is that there is no supervised
anomaly data at all.

The consequence is that the first dataset comes from replaying a rules-based
detector over the historical archive and having a human review its output.
Those labels are weak by construction, and `training/labels.py` keeps
`verified`, `weak`, and `synthetic` provenance separate so a report can never
blur them.

A dataset containing only candidate alerts cannot teach normal from abnormal.
Collect normal hard cases deliberately: legitimate long runs, scheduled water
use, reduced generation, overlapping loads.

## Know which evidence is actually measured

On the deployment this was built against, two appliance heads out of twenty-two
had a dedicated measurement channel. The rest rested on physics-informed
synthetic labels generated by a rules layer.

That matters because the same rules layer generates the labels the model is
trained on. Agreement between the model and those rules is not independent
confirmation of anything. The snapshot contract marks every estimate with its
kind for this reason, and the agent prompt is explicit that a measured state
outranks an inferred one.

## Home Assistant is inside the building

Home Assistant, and anything else on the building's LAN, is not reachable from
a developer laptop over a mesh VPN that only exposes specific hosts. An
evidence provider that needs it must run on a host inside that network.

Build for its absence. `evidence/ha.py` records entities as unavailable rather
than omitting them, so an agent can distinguish "no leak sensor installed" from
"leak sensor reports dry". A commanded state or a setpoint is never proof of
physical operation, and occupancy is never proof that appliances are off.

## Make a total failure visible

An early version of the coordinator returned zero incidents when every agent
call failed, because failures were only ever attached to clusters that already
existed. A serving endpoint that was down therefore looked exactly like a quiet
house.

It now emits one incident with headline `insufficient_evidence` listing the
failed panels, and a test holds that behavior in place. Any monitoring system
needs the same property: the absence of an alert must be distinguishable from
the absence of a working detector.
